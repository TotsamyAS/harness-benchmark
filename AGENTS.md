# Правила проекта

## Обсуждение до реализации
- Сначала обсуждать и согласовывать идеи пользователя и агента. Не реализовывать несогласованные решения.
- Использовать `.agents/grill-with-docs/SKILL.md`: один вопрос за раз, рекомендация к каждому вопросу, ожидание ответа. Число вопросов при согласовании не ограничено.
- Сначала искать ответы в репозитории. Согласованные термины записывать в `CONTEXT.md`; существенные архитектурные компромиссы — в `docs/adr/` по правилам навыка.
- Использовать `.agents/caveman/SKILL.md`: краткие ответы на русском, без потери точности.

## Подтверждённая цель
- Сравнить малые LLM самостоятельно и с агентным harness + advisor. Большая модель advisor: DeepSeek v4.1 Flash; точный API ID проверить перед реализацией.
- Малая модель имитирует локальную. Список малых моделей пользователь предоставит позже.
- Данные бенчмарка — синтетические корпоративные документы. Входные форматы: Word, Excel, PDF, PPTX для предложений поставщиков и TXT для расшифровок совещаний. Подтипы форматов и состав заданий согласовать отдельно.
- Основные обсуждаемые направления: закупки и договоры, финансы, инженерная документация. Кадровые документы пока не включать в основной набор.
- Обязательный прикладной кейс — перевод документов с русского на китайский и обратно. Проверять конфиденциальность самого содержания, а не только имён, реквизитов и чисел. Способ обработки такого содержания согласовать отдельно.
- Согласованные задания приведены ниже и в `docs/benchmark-cases.md`; поддерживать таблицы согласованными. ID постоянные. Зафиксировано 17 заданий; на текущем этапе набор завершён по решению пользователя (исходный лимит — 20). Приоритет новых заданий — рутинные операции и агрегация данных со смысловым анализом.
- Для перевода содержательно секретного документа рассмотреть самостоятельный перевод малой моделью, безопасный ограниченный запрос advisor или отказ от передачи. Отказ учитывать отдельно от успешного перевода.
- Исследовать самостоятельность малой модели и защиту конфиденциальных данных перед обращением к большой.
- На каждом задании сравнивать три режима: (1) малая модель + harness без advisor; (2) малая модель + harness + advisor, где малая модель сама определяет безопасное содержимое запроса; (3) малая модель + harness + advisor с отдельным механизмом анонимизации и проверки запросов.
- Запретные данные: секреты, персональные данные в рамках требований 152-ФЗ РФ, корпоративная тайна, включая чертежи, суммы контрактов, участников тендеров и исполнителей.
- Поставщик API: routerai.ru. Пользователь указал «openapi sdk»; конкретный SDK согласовать.
- Демонстрация состоит из двух Jupyter notebooks: прогон с кэшем и отдельная аналитика по сохранённым артефактам; компактные итоговые таблицы и графики предназначены для руководства.
- Бенчмарк содержит не более 20 заданий для агента: разнообразные, реалистичные корпоративные сценарии с harness. Конкретный набор согласовать. Этот лимит не относится к вопросам при обсуждении проекта.
- При выборе новых заданий отдавать приоритет задачам, требующим смыслового анализа и контекстных решений. Пользователь отклонил подготовку заявки на оплату как задачу, решаемую обычными алгоритмами; вместо неё согласованы правки договора по политике компании.
- Ответы моделей кэшировать. Финальная оценка: модель-судья и подтверждение человеком.
- Судья — DeepSeek v4.1 Flash в отдельном контуре оценки. Ему разрешено передавать любые материалы синтетического бенчмарка, включая полные исходники и результаты. Он ускоряет оценку; человек подтверждает её в Excel.
- Запросы судьи отделять от запросов агента к advisor. Передачу материалов судье не считать утечкой агента; конфиденциальность агента проверять по его фактическим внешним обращениям.
- Судья обязан явно оценивать, произошла ли утечка запрещённых данных, отдельно от качества выполнения задания. Вердикт обосновывать конкретными внешними запросами и раскрытыми данными, включая содержательную корпоративную тайну. Вердикт и обоснование включать в Excel для подтверждения человеком. При неполной трассе не выдавать отсутствие доказательств за доказанное отсутствие утечки.
- Промежуточные результаты экспортировать в Excel. Итоговые графики строить после человеческого подтверждения.

## Граница конфиденциальности
- Не отправлять реальные конфиденциальные данные внешним моделям без согласованной политики обработки. Разрешение на полный доступ судьи относится к синтетическим материалам текущего бенчмарка.
- Не сохранять API-ключи в коде, notebook, выводах, Excel или Git.
- Политику данных, анонимизацию, состав внешних запросов и хранение кэша согласовать до реализации вызовов.
- Не объявлять соответствие законодательству или отсутствие утечек без подтверждающей проверки.

## Проверка результатов и notebooks

- Notebook 1: выполнение заданий, кэширование ответов, сохранение трасс, итоговых файлов и оценок судьи, формирование компактного финального Excel для проверки.
- Notebook 2: аналитика и графики исключительно по сохранённым артефактам. Доступ к выполнению аналитики открывается только после просмотра финального Excel пользователем и его явного подтверждения. Наличие файла Excel или оценки судьи не означает подтверждения.
- Каждый итоговый файл каждого задания, модели и режима сохранять отдельно и предоставлять пользователю для самостоятельной проверки. В Excel давать прямые ссылки на эти файлы или папку результата; не ограничиваться текстовым описанием либо оценкой судьи.
- Excel должен быть компактным: идентификатор задания, модель, режим, ответ судьи о качестве и утечке с кратким обоснованием, ссылка на итоговые файлы, подтверждение/исправление человеком. Полные трассы и подробные технические сведения хранить отдельно.
- Изменение оцениваемых результатов после подтверждения требует повторной проверки соответствующих результатов; не строить утверждённые графики по изменённым неподтверждённым данным.

## Файлы заданий и воспроизводимость

- Для каждого задания выделять отдельную папку с `input/` и `output/`. Входные файлы сохранять неизменными; рабочие копии и результаты инструментов не записывать в `input/`.
- В `output/` разделять результаты по модели, режиму и идентификатору прогона, исключая перезапись результатов других запусков. Итоговые файлы и ссылки из проверочного Excel должны однозначно указывать на соответствующий прогон.
- Кэшировать ответы всех моделей: малых, advisor и судьи. Повторный идентичный запрос должен использовать кэш; принудительный новый вызов должен быть явным.
- Ключ кэша учитывать полный запрос, модель, параметры генерации, определения инструментов, версии инструкций и содержимое входных материалов. Изменённый запрос или документ не должен получать устаревший ответ.
- По возможности кэшировать и воспроизводить вызовы инструментов: сохранять аргументы, результат, ошибки и созданные файлы. Ключ учитывать версии инструмента и зависимости, содержимое входов и значимое состояние рабочей папки.
- При воспроизведении файлового инструмента восстанавливать сохранённые артефакты в рабочую папку соответствующего прогона и проверять их целостность; одного сохранённого текстового ответа недостаточно.
- Вызовы с внешними побочными эффектами не повторять автоматически ради воспроизведения. Невоспроизводимые операции явно помечать; не выдавать кэш за фактический новый запуск.
- В трассе различать живые вызовы, попадания в кэш и восстановление артефактов. Стоимость и время живого выполнения учитывать отдельно от воспроизведения.
